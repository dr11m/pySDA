# Проверка сценария смены пароля Steam

Проверка 2026-10-20: **отсутствие ограничения торговли после CLI-операции не доказано**.
Найдено и исправлено расхождение маршрута с интерфейсом Steam. Реальных смен
пароля, отправки кодов, мобильных подтверждений и деавторизаций при аудите не было.

## Что подтверждено

[Официальные правила Steam](https://help.steampowered.com/en/faqs/view/451E-96B3-D194-50FC)
разделяют смену известного пароля и сброс забытого. Для сброса указаны ограничения
торговли и Market на 5 дней; после неактивности более двух месяцев — 30 дней.
Для обычной смены через настройки клиента это ограничение не заявлено.

Кнопка смены пароля в JavaScript установленного клиента использует URL registry
`HelpChangePassword`. Исследован файл `steamui/chunk~2dcc5aaf7.js`, SHA-256
`5b4db9a7e27b0d92254fdfc1babfe942027e507a82560b8a64e8ccc090bd6aeb`.
Это свидетельство установленной версии, а не обещание неизменности клиента.

С существующими сохранёнными cookies выполнены только GET:

1. `HelpChangePassword` перенаправил на `HelpWithLoginInfoSendCode/` с `reset=1`.
2. Страница предложила смену пароля и ссылку `HelpWithLoginInfoEnterCode` с
   `reset=1`, `lost=0`, `issueid=406`.
3. GET страницы ввода кода показал форму подтверждения. JavaScript не исполнялся,
   запрос отправки кода не выполнялся.

Для сравнения публичная страница забытого пароля `HelpWithLoginInfo?issueid=406`
содержала скрытые поля `reset=0`, `lost=0`, `issueid=406`. Следовательно,
имя `reset` нельзя интерпретировать как доказательство торгового ограничения.

В публичном `help.js` методы `GetNextStep` и `VerifyPasswordRSA` передают
полученные аргументы `reset` и `lost`, не заменяя `lost` константой `2`.

## Исправление

До исправления pySDA принудительно посылал `lost=2` на двух стадиях, хотя
ссылка штатного мастера содержала `lost=0`. Влияние этой подмены на серверную
классификацию операции не проверено; утверждать, что она обязательно вызывала
ограничение, нельзя. Но такое отклонение от штатного сценария необоснованно.

Теперь параметры берутся из одной однозначной ссылки продолжения от Steam.
Отсутствующий `lost` больше не подменяется предположением. Разрешён только
наблюдавшийся начальный маршрут `reset=1`, `lost=0`, `issueid=406` с непустыми
`s` и `account`. Иные режимы останавливают процесс. Эти значения сохраняются
при переходе к следующему шагу и проверке известного текущего пароля.

Регрессии офлайн проверяют сохранение параметров, отказ до POST при неизвестном
маршруте и разбор обезличенной ссылки из реального ответа. Исходный приватный
HTML также разобран новым кодом без сетевых запросов.

## Что ещё требуется для проверки на реальном аккаунте

Отсутствие подмены параметров не доказывает, как Steam классифицирует завершённую
операцию. Офлайн-тесты также не подтверждают отсутствие серверного ограничения.

Для проверки нужен отдельно согласованный тестовый аккаунт без важных торговых
операций: записать исходную доступность торговли и Market, выполнить одну смену
известного пароля, затем проверить оба ограничения и их причины. Сам торговый
запрос для этого отправлять не требуется. maFile не меняется. По одному аккаунту
можно подтвердить только наблюдённый случай, а не все возможные состояния Steam.

До такого сравнения CLI нельзя описывать как проверенный способ смены пароля
без ограничения торговли. Для важных аккаунтов официальный путь — настройки
клиента Steam с вводом известного текущего пароля, без восстановления доступа.
